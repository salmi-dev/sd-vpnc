# Design

## Context

`run_container` currently starts the VPN container attached to the requested command. The entrypoint starts OpenVPN, waits for the tunnel, then executes one local shell, SSH command, or SSH-tmux command; its exit trap stops OpenVPN. `shell_cmd` can attach a shell to an existing container, but there is no session registry or last-session shutdown. See `proposal.md` and the spec delta for the contract.

## Goals / Non-Goals

**Goals:**
- Keep one regular VPN manager container and one OpenVPN process alive across concurrent managed sessions.
- Make first-start, attach, lease registration, final release, and shutdown race-safe.
- Recover provably stale leases after abnormal client/host termination without stopping a container that still has a live managed session.
- Preserve shell, remote SSH, and SSH-tmux behavior while making first-manager options explicit.

**Non-Goals:**
- Change the separate tunnel-container lifecycle or add tunnel-port operations.
- Change the VPN/image format, persist the container home, or let later clients replace a live manager's mounts.
- Forward additional host environment variables or add DevPod/WireGuard support.

## Decisions

### Run a persistent manager entrypoint; execute every client separately

The first managed request creates the named regular VPN container with detached and auto-remove options and a manager entrypoint mode. That mode seeds the runtime home, starts OpenVPN, waits for the existing VPN readiness condition, creates the session-registry runtime directory, reports manager readiness, and remains as the container's main process independently of the host coordinator. Its signal/exit handling owns OpenVPN cleanup. It does not execute a shell or SSH command.

After manager readiness, each invocation starts a session launcher through `podman exec` or `docker exec`, explicitly with `/work` as its exec working directory. The launcher registers a unique lease before starting the requested command. The host coordinator removes it after normal engine-exec return or handled termination; if that coordinator disappears, the manager watcher reconciles it. A lease covers the foreground shell/SSH/SSH-tmux command, not the manager PID. Thus the first and later sessions follow the same exec path, and ending the first session cannot stop OpenVPN while another lease exists. Bare `ssh` still selects the local login shell; `ssh` with arguments still invokes remote SSH; `ssh-tmux` retains its current host/session command construction.

Give the manager a recognizable ownership marker (container label and manager protocol/version) and a fresh runtime session-state directory. Reconcile, stop, or remove only a container whose manager ownership can be verified. If the expected name belongs to an unrecognized/legacy container, or inspection fails, fail without stopping or attaching to it. The manager session-state directory is recreated on manager startup so a restarted container cannot inherit process leases from its prior process lifetime.

After VPN readiness, enter `WAITING_FIRST_SESSION` and start a bounded 30-second registration grace period. The container is configured for automatic removal when PID 1 exits, including watcher-driven cleanup. The idle watcher does not stop the manager before the first lease registers during this grace. If the host registers a first lease, atomically change the state to `ACTIVE` and remember that at least one session has existed. If the initial engine exec/registration fails, the host asks the manager to stop when it can verify the registry is empty; if the host coordinator itself disappears, the grace expiry atomically changes the still-empty manager to `STOPPING` and PID 1 exits. A session arriving after that transition is rejected, and the host reports that startup/registration failed instead of running an unleased command.

### Serialize lifecycle transitions with an explicit host lock dependency

All managed manager creation and host-side start/attach/final-stop transitions use one per-user lock file in the private `sd-vpnc` state directory. The lock is held only for the transition, not for the interactive session. While holding it, a caller checks manager ownership/configuration, creates or starts the manager if needed, and waits until its session launcher has registered a lease. A caller whose session ends reacquires the same lock, asks the in-container registry to reconcile leases and atomically mark an empty manager `STOPPING`, then stops it. An attach therefore cannot slip between the last-session count and stop; if it arrives after the `STOPPING` transition, it starts a new manager after the old one is stopped.

The in-container registry has its own lock and `WAITING_FIRST_SESSION`, `ACTIVE`, and `STOPPING` states. Registration is allowed in `WAITING_FIRST_SESSION` during the startup grace or in `ACTIVE`; a first successful registration changes the state to `ACTIVE` and sets `ever_registered`. An attach that reaches the registry before a stop transition is counted; one that arrives after `STOPPING` is rejected before its command can run. If the watcher wins after the host has observed a matching ready manager but before registration, the host verifies the owned manager is `STOPPING` (or has already stopped/auto-removed), waits for its removal while retaining the host lock, starts a replacement, and retries registration exactly once. The rejected launcher creates no lease and cannot execute its user command; a second rejection follows normal failure cleanup rather than retrying again. The watcher and host last-session cleanup both reconcile and change `ACTIVE` to `STOPPING` under this same lock only when `ever_registered` is true and no live or indeterminate lease remains. The watcher runs independently of the host coordinator, so a dead host process cannot strand an empty manager. This state transition also prevents an in-flight exec request from starting an unleased command if its host client exits and releases the host lock.

Use the external host `flock` command rather than a shell `mkdir` lock. POSIX shell has no crash-released mutex, and removing a stale directory lock based on a separate liveness check can race another contender replacing that lock. `flock` releases the kernel lock when the owning process exits or the host reboots, while its lock file may safely remain. Check for the executable before any runtime lifecycle mutation and fail with an actionable message if absent. Document this as a host runtime dependency (not a POSIX-shell builtin); do not silently fall back to an unsafe locking scheme. Use the packaged lock utility for the short in-container registry updates as well.

### Keep a process-identity lease registry and fail closed on uncertainty

The manager stores each lease under its fresh runtime state directory with a unique session ID and the exact identity of the session launcher: PID plus process start identity (Linux `/proc` start ticks) within that manager generation. The launcher records itself before replacing itself with the requested foreground shell/SSH/tmux command using `exec`; the PID and start identity therefore remain the same for the full command lifetime. The host removes the lease after a normal engine-exec return. If the host client dies first, the in-container command remains identifiable and keeps its lease; if the command is gone, a later reconciliation can reap the stale record. The registry is protected by the in-container lock. The host lifecycle lock is retained until the session launcher has registered a lease and received host acknowledgement. The background engine-exec child closes inherited fd 9 so an abruptly terminated host does not leave the lock held by an orphaned exec client; the host parent retains the lock through registration and acknowledgement.

If the host client is killed abruptly, the lease remains. Before counting sessions, the manager compares the recorded PID and start identity with the current process table; a missing PID, a zombie, or a PID with a different start identity is stale and can be removed. The manager generation is part of the record, so a restart cannot mistake an old PID for a live lease. Host-process death alone is never grounds to remove a lease, because a disconnected engine client can leave its exec process alive.

Only leases proven stale are reaped. A live matching process keeps the lease. If process inspection or the container query fails, or identity cannot be compared, classify the lease as indeterminate, report the session ID, and preserve the manager; do not force-stop it. A manager-side watcher polls the registry once per second, under the same lock used for registration, host cleanup, and `status`. Once `ever_registered` is true, it reaps provably stale records and atomically changes `ACTIVE` to `STOPPING` when no live or indeterminate lease remains; PID 1 then exits and the detached container stops independently of the host coordinator. `status` reports manager ownership and live/stale/indeterminate session counts and can also trigger reconciliation. A failed initial launch is stopped by the host when possible or by the first-registration grace timeout if the host disappeared. Container stop is allowed only after a successful locked query confirms zero live or indeterminate leases.

This separates session accounting from the host shell/engine-client lifetime: host exit may close an exec connection, but it cannot erase a live container-side lease. If that in-container session later exits without a host coordinator to remove its lease, the watcher detects the stale process identity and shuts down once the registry is conclusively empty. A full container/host restart creates a fresh manager generation and empty runtime registry because no prior in-container client process can still be live.

### Freeze startup options for the lifetime of a manager

The first client determines the manager's effective runtime configuration. Save a private, mode-0600 manifest bound to the manager ID and compare it under the lifecycle lock before attaching subsequent sessions. It covers the selected engine/context and numeric user, image/rebuild state, canonical effective `/work`, VPN configuration/credentials source paths and config-directory mount, SSH mount source, rootless mount mode, and the condition/value of `DEVPOD_WORKSPACE_ID`. Do not put credential contents in the manifest or in diagnostics. A later mismatch fails with a generic explanation that the current manager uses different startup options; it never silently reuses mounts chosen by the first caller and never replaces a manager with live sessions.

The VPN configuration is copied and used by OpenVPN at manager startup, so edits to that file do not reconfigure an active VPN. SSH configuration remains on the existing read-only bind and is read when a new SSH session starts. A caller supplying `--rebuild` while any live or indeterminate lease exists is rejected before rebuilding. If reconciliation proves the manager idle, stop/remove that owned manager before rebuilding; an absent manager needs no stop. The `image --rebuild` and `tun --rebuild` commands use the same host lifecycle lock from idle-manager validation/removal through build completion, so no concurrent managed start can attach or start against the image while it is being rebuilt. The lock is released explicitly after a successful build and by normal descriptor cleanup on failure. A tunnel request then starts from the rebuilt image. This avoids implying that a running container has picked up a rebuilt image.

### Preserve the existing tunnel-target interaction as a follow-up

The existing `shell_cmd` prefers `TUN_CONTAINER_NAME` when a tunnel container is running. This proposal leaves that selection and the separate tunnel workflow unchanged; otherwise `shell` targets the regular VPN manager. Consequently, when the tunnel container is active, `shell` may still attach there rather than create/attach the regular manager. Aligning shell target selection with the regular manager is a separate decision/follow-up, not an implicit tunnel behavior change in this proposal.

## Risks / Trade-offs

- A persistent detached manager changes the entrypoint's lifetime contract → make manager mode explicit, keep OpenVPN cleanup in PID 1, and test that multiple exec sessions do not start/restart VPN and that both explicit stop and watcher-driven PID 1 exit clean up OpenVPN.
- Host `flock` is not guaranteed on every POSIX-shell host, especially a stock macOS installation → require and document a compatible executable, detect it before runtime changes, and fail closed. This is less portable than a pure shell script but is chosen because a crash-recoverable critical section is required for safe concurrent start/stop.
- PID reuse can make PID-only lease files unsafe → record process start identity and manager generation; test PID reuse, host/container restart, killed clients, and live orphaned exec processes. If identity is uncertain, leave the manager running.
- A broken container engine or unreadable process table can retain the manager longer than necessary → report the unresolved session ID and retry reconciliation; favor a safe leak over stopping a live shared container.
- A later caller may use a different working/config/SSH path or workspace identifier → reject the mismatch without printing sensitive values; document that startup options are selected by the first live manager.
- `shell` may prefer the independent tunnel container → preserve that pre-existing behavior here and track target unification separately.

## Validation Strategy

- Fake-engine lifecycle regression tests cover first manager startup, concurrent shell/SSH/SSH-tmux attachment, exactly one manager start, `exec` per session, watcher-driven last-session shutdown, startup grace/failed launch, the watcher-winning-STOPPING host retry (with the rejected command proven not to run), and deterministic registration-versus-idle-shutdown races.
- Lease tests cover normal release, SIGTERM cleanup, SIGKILL/stale-session recovery, host/container generation changes, PID reuse, host frontend death before registration acknowledgement while the engine exec survives without retaining fd 9 or running an unacknowledged command, host frontend death followed by final in-container session exit and automatic manager cleanup, query/identity uncertainty, and the invariant that uncertain or live leases never cause stop.
- Configuration tests cover matching and mismatching `-C`, VPN/config/credentials source, SSH config, engine/user, and workspace identifier options; `--rebuild` is rejected with live leases and only rebuilds after an idle manager is stopped.
- Shell behavior tests cover local login-shell selection, remote `ssh HOST`, and `ssh-tmux`; a functional generated-entrypoint test stubs OpenVPN/tun readiness, runs the generated registry watcher, and observes the OpenVPN cleanup trap when PID 1 exits. Deterministic build-vs-start tests hold image rebuilding at a fake-engine gate, prove manager startup occurs only after build completion, and verify a failed build releases the lock through process cleanup; exec cwd remains `/work`.
- Run syntax checks, both behavior suites, CLI smoke checks, diff-check, and `openspec validate shared-vpn-container-sessions --strict`. Attempt `shellcheck sd-vpnc tests/test-dotfiles-build.sh tests/test-container-session-manager.sh` and report accurately if the executable/version is unavailable.
- When Podman/Docker and the application image are already available, run conditional manager lifecycle smoke checks using only the local image and `--pull=never`; skip clearly when unavailable.
